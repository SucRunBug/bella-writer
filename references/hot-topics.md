# 大纲前热点扫描

第二步用。目的不是改选题，而是在写大纲之前先知道：此刻各平台正在热什么，用户的选题有没有可以自然挂上去的热点。挂不挂得上，由第三步诊断决定，这一步只负责把榜单扫出来、把候选热点列出来。

**核心纪律：只提供线索，不做决定。** 这一步绝不直接把热点塞进选题，更不允许为了蹭热点扭曲选题本身。

**联网是硬要求。** 这一步必须真的联网拿实时数据，没有离线替代方案。60s API 的某个接口挂了可以跳过那一个，但如果全部拿不到，要联网换其他途径（搜索引擎、平台网页）把当前热榜情况摸清楚，不能空着交差。用户没给对标内容时，同样要联网搜同选题已经火过的爆款，摸清这类选题怎么做、哪些角度被做烂，作为第三步诊断的参考。

---

## 数据源：60s API

开源项目 [vikiboss/60s](https://github.com/vikiboss/60s) 提供各平台实时热榜，公共实例 `https://60s.viki.moe`，返回 JSON，热度值是平台真实数据。

按目标平台优先级调用（curl 即可）：

```bash
curl -s "https://60s.viki.moe/v2/rednote"   # 小红书热点榜（rank/title/score/链接）
curl -s "https://60s.viki.moe/v2/weibo"     # 微博热搜（title/hot_value/链接）
curl -s "https://60s.viki.moe/v2/douyin"    # 抖音热搜（title/hot_value/封面/上榜时间）
curl -s "https://60s.viki.moe/v2/zhihu"     # 知乎热榜（title/问题摘要）
curl -s "https://60s.viki.moe/v2/toutiao"   # 头条热榜（title/hot_value/链接）
curl -s "https://60s.viki.moe/v2/bili"      # B站热搜（不稳定，可能 500）
```

注意事项：

- 公共实例依赖上游接口存活，个别接口挂掉（返回 500）很正常，跳过即可，不要卡住。
- 目标平台明确时优先扫对应平台的榜；全平台模式至少扫微博 + 目标平台。
- 榜单给的是「话题词条 + 热度值」，不是内容作品。不要把榜单标题当成内容素材。

---

## 怎么筛候选热点

扫完榜单，按这个标准筛出 0-3 个候选：

1. **真实相关**：热点和选题有实质交集（同领域、同人群、同争议点），不是谐音梗式的硬扯。
2. **方向一致**：挂上热点后，选题的核心观点不需要改。需要改观点才能蹭的，直接放弃。
3. **时效合理**：热点还在上升期或平台期。已经被全网做烂的角度，蹭进去只会被淹没。

筛不出来就如实说「本轮无可用热点」，这是完全正常的结果，大多数选题都蹭不上热点。

---

## 产出格式

```text
热点扫描：{选题} @ {目标平台}

一、扫了哪些榜
| 平台 | 接口状态 | 榜单时间 |
|---|---|---|

二、候选热点（0-3 个，没有就写「无」）
| # | 热点标题 | 平台 | 热度值 | 与选题的交集 | 可能的挂法 |
|---|---|---|---|---|---|

三、给第三步诊断的建议
- 推荐蹭：{哪个热点、怎么挂、为什么不算硬蹭}
- 或：本轮无可用热点，按原选题直接走。
```

---

## 红线

- **不硬蹭。** 候选热点只是给第三步诊断的输入，诊断认为不合适就放弃，没有任何商量余地。
- **不为蹭热点改核心观点。** 热点只能当切入口或案例由头，不能当主心骨。
- **热度值照实写。** 接口给多少写多少，接口挂了就写「未获取」。
- **榜单标题不是事实素材。** 热点事件的具体细节（数据、人物、时间线）要在第四步找一手来源核实后才能进成稿。
- **必须真联网。** 拿不到榜单不等于这一步可以省，要联网换途径补；凭记忆编一个榜单是绝对禁止的。
